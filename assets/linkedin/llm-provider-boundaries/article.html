Decoupling LLM providers from business logic.

Production AI becomes easier to test, change, and observe when one small interface owns the provider relationship instead of every route and service class.

Calling a provider SDK directly is fast at first. The bill arrives when business rules, retry behavior, prompt shaping, and vendor-specific response types have spread through the application.

01 — The problem

Speed can harden into a dependency.

Many AI features begin inside a router: receive input, call a model SDK, return text. It feels efficient because the first feature is small. But the route has quietly learned too much—how a provider authenticates, retries, streams, meters tokens, and represents failure.

The costly assumption: an SDK call is just an implementation detail. In a growing product it becomes a policy decision, so it deserves one clear home.

01

Vendor lock-in

Replacing a provider becomes a multi-file rewrite rather than a controlled swap.

02

Fragile tests

Core workflows cannot be exercised without mocking a third-party client everywhere.

02 — The boundary

Make the provider a detail.

A narrow application-facing interface turns the vendor into an adapter. The product asks for a capability—generate a completion, classify a request, embed a document—without knowing which SDK fulfills it. Provider code remains at the edge; business code depends on an abstraction it owns.

  • Keep application types stable and provider-neutral.
  • Map credentials, retries, timeouts, and model selection in the adapter.
  • Inject the capability into services so a deterministic fake can support tests.

03 — The contract

Design around the work, not the SDK.

The interface should be intentionally small. It describes what the application needs and no more: input, output, useful metadata, and recoverable failure. That restraint keeps a convenience wrapper from becoming another leaky provider client.

INPUT

Intent

Accept domain concepts such as task, context, and policy—not a vendor request object.

OUTPUT

Evidence

Return content alongside model identity, latency, and token accounting when it matters.

FAILURE

Recovery

Translate provider failure into an application error with a clear fallback path.

TEST

Control

Use a small fake to test decisions without a network or a bill.

04 — Production effects

The boundary creates options.

Once the provider is isolated, reliability work is no longer scattered. Fallback routing, model experiments, approval gates, redaction, telemetry, and cost limits can be introduced at one seam. The lesson is not to abstract every future. It is to put the external dependency behind the one boundary the product already needs.
